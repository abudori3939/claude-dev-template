# スタックガイド: KiCad / 基板設計

成果物が**プログラムではなく回路図・プリント基板（KiCad プロジェクト）**であるプロジェクト用のスタックガイド。
CLAUDE.md の開発フロー（ドキュメント駆動・TDD・ブランチ→PR→レビュー）を、ここで基板設計向けに読み替えて具体化する。

> 付属資料（このガイドとセットで使う）:
> - [`kicad/workflow_sch.md`](kicad/workflow_sch.md) … kicad-cli / スクリプトによる回路図編集の作法とコード雛形
> - [`kicad/ci_kicad.md`](kicad/ci_kicad.md) … GitHub Actions（ERC / DRC / テスト / 出図）の設定手順
> - [`kicad/review_checklist.md`](kicad/review_checklist.md) … 出図前・発注前チェックリスト
> - [`kicad/scripts/`](kicad/scripts/) … ネットリスト検証ヘルパ（接続テストの土台）と リポジトリ衛生チェック（OS 混在対策の自動ゲート）

## このスタックの性格（コードと文書成果物の中間）

KiCad のファイル（`.kicad_sch` / `.kicad_pcb`）は**テキスト（S式）**であり、git 差分・PR レビューが成立する。
`kicad-cli` で ERC / DRC・ネットリスト・出図が CLI 実行できるため、**TDD は比喩ではなく本物のテストとして成立させる**
（接続テストを先に書いて失敗を確認 → 回路図実装で通す）。

ただし工程ごとにエージェント適性が異なるため、責務を工程で分ける:

| 工程 | 主導 | エージェントの役割 |
|---|---|---|
| 要求・ブロック設計・部品選定 | エージェント | 対話で要件を引き出し plan / spec / parts.md に整形。データシート読解はサブエージェント |
| 回路図（スケマ） | エージェント | スクリプト経由で `.kicad_sch` を編集（下記アーキテクチャ） |
| ライブラリ（シンボル/フットプリント） | エージェント＋**人間承認** | 寸法ミスが最も高くつくため、フットプリントは人間照合ゲート必須 |
| レイアウト（配置・配線） | **人間（GUI）** | エージェントは配置方針 md の作成・DRC・ネット一致検証・出図レビューで挟む |
| 検証（ERC / DRC / 接続テスト / BOM） | エージェント（スクリプト） | このスタックの主戦場。CI と同一コマンド |
| 製造出力（ガーバー等） | スクリプト / CI | 完全に決定的。モデルにやらせない |

## アーキテクチャ（3層）

```
┌ 正（source of truth） *.kicad_pro / *.kicad_sch / *.kicad_pcb   ← git 管理・PR レビュー対象
├ 操作層               Python スクリプト（kiutils 等）＋ kicad-cli ← エージェントは GUI を持たないので必ずここを通る
└ 検証層               ERC / DRC / ネットリスト pytest / 出図の目視 ← 「テスト」の実体。CI でも同じコマンド
```

- KiCad の正史ファイルを唯一の真実の源に保つ（人間はいつでも KiCad GUI で開ける）。
- 回路を独自 DSL（SKiDL / atopile 等）で記述する方式は採らない（正史ファイルから外れるため）。採る場合は ADR に記録する。

## 開発フローの読み替え（コード ↔ 基板設計）

CLAUDE.md のフローは変えない。各工程を次のように対応させる。

| コード開発 | 基板設計 | 備考 |
|---|---|---|
| plan.md（どう作るか） | 基板の目的・要求仕様（電源/寸法/コネクタ/環境）・**回路ブロック分割と実装順** | ブロック＝電源、MCU、通信、センサ… |
| spec.md（2層で育てる） | **層1（Phase 0）**: 外部インターフェース（コネクタ・電圧・信号）と**ブロック間ネット（境界の契約）** / **層2（着手時）**: ブロックごとの部品選定・ピン割当・接続表 | 関数 I/O ＝ ピン割当・接続表 |
| progress.md | 現工程（回路図/レイアウト/出図）・ブロックごとの状態・未解決事項 | |
| **レッド**（失敗するテスト） | ①ブロックの回路仕様（部品・ピン割当・接続表）を spec に書きユーザー承認 ②**その接続を検証する pytest を先に書き、失敗を確認** | 未実装ネットなのでテストは本当に落ちる |
| テスト承認 | 接続テスト＋回路仕様の承認。**フットプリント選定もここで確認**（最重要ゲート） | 直すならここが最も安い |
| **グリーン**（最小実装） | 回路図にブロックを実装し、接続テスト＋ERC が通る | [workflow_sch.md](kicad/workflow_sch.md) の作法で編集 |
| **リファクタリング** | リファレンス指定子の整理・シート整理・図の可読性向上 | テスト緑のまま。GUI で人間が整えても可 |
| lint / 静的解析 | **ERC / DRC 警告ゼロ** ＋ カスタムチェック（BOM 欄埋まり・未接続ピンの NC フラグ） | `kicad-cli sch erc` / `kicad-cli pcb drc` |
| コードレビュー（PR） | S式 diff ＋ **出図した PDF/SVG を見るレビュー** | 画像目視はサブエージェント＋人間 |

- 「コンパイルエラーはレッドと認めない」は「**ファイルが開けない・ネットリストが出力できない状態はレッドと認めない。テストはネットリストが出力されたうえで接続アサーションが失敗していること**」と読み替える。

### レイアウトフェーズの読み替え（回路図とは別サイクル）

- **レッド** ＝ 配置方針（フロアプラン: 主要部品の配置図・層構成・配線ルール・禁止領域）を md でユーザー承認
- **グリーン** ＝ 配置・配線して **DRC ゼロ ＋ 回路図とのネット一致**（配線作業は人間の GUI 作業を既定とする）
- **リファクタ** ＝ シルク整理・仕上げ
- 自動配線（freerouting 等）を使う場合は plan.md に明記し、結果は必ず DRC＋人間目視を通す。

### 粒度

- **回路図: 1サイクル（=1 PR）＝1回路ブロック**（電源、MCU など。人間が回路図 1〜2 シートをレビューできる量。コードの M 相当）。
- **レイアウト: 配置で 1 PR ＋ 配線で 1 PR** を既定とする（小規模基板は合わせて 1 PR でよい。plan.md に明記）。

### クロスプラットフォーム運用（Windows / Ubuntu 混在前提）

**方針: OS の混在は許容する。ただし「混ざっても大丈夫」を人間の注意力ではなく CI の緑/赤で保証する。**

OS を1つに縛る（例:「必ず Windows で作業する」）制約は、**守られている間しか効かず、破られたことを検出できない**ため採らない。代わりに、混在で実際に壊れる4点を機械が毎 PR で検査する（[`check_repo_hygiene.py`](kicad/scripts/check_repo_hygiene.py)、CI 組み込みは [ci_kicad.md](kicad/ci_kicad.md)）。**スクリプトはコピーせず `agent_docs/stacks/kicad/scripts/` を直接呼ぶ**（コピーの二重管理を避ける）:

| 混在で壊れるもの | 対策 | 検査方法 |
|---|---|---|
| 改行コード（CRLF 差分ノイズ） | `.gitattributes` で LF 固定（下記1） | git の**インデックスの実体**に CRLF が無いか |
| 一時・バックアップファイル | `.gitignore`（下記2） | ignore 対象なのに追跡されているファイルが無いか |
| ライブラリ参照の絶対パス | `${KIPRJMOD}` 相対（下記3） | ドライブレター・ホームディレクトリの混入が無いか |
| **KiCad のバージョン差** | バージョン固定（「環境」節） | 全ファイルの `(version ...)` が揃い固定値と一致するか |

> ⭐ **混在の実害は「OS の違い」ではなく「KiCad バージョンの違い」。** バージョンが違えばファイル全体が書き換わり差分が追えなくなるが、これは Windows どうしでも起こる。逆にバージョンさえ揃っていれば、KiCad は全 OS で同じ内容（LF）を書き出すため、Windows のコミットと Ubuntu のコミットはバイト単位で比較可能になり、差分には本質的な変更だけが残る。**縛るべきは OS ではなくバージョン。**

差分・参照が OS 差で壊れないよう、**リポジトリ初期構築時にエージェントが次の2ファイルを必ず整備する**（レビュー時の確認項目は [review_checklist.md](kicad/review_checklist.md) §0）。

1. **`.gitattributes`** — 改行コードだけの差分（CRLF ノイズ）を根絶する。KiCad ファイルはテキスト（S式 / JSON）なので、全 OS で LF に固定する。**このテンプレート由来のリポジトリにはルートに同梱済み**（無ければ作成する）:

   ```gitattributes
   # KiCad ファイルは全 OS で LF に固定（改行コードのみの差分を出さない）
   *.kicad_*     text eol=lf
   sym-lib-table text eol=lf
   fp-lib-table  text eol=lf
   *.net         text eol=lf
   # スクリプト・ドキュメント・CI 設定も LF
   *.py  text eol=lf
   *.md  text eol=lf
   *.yml text eol=lf
   # 例外: 改行コードが意味を持つファイル
   *.bat text eol=crlf   # Windows バッチは CRLF 前提
   *.cmd text eol=crlf
   *.sh  text eol=lf     # CRLF だと shebang 解釈に失敗する
   ```

   **なぜ KiCad ファイルを LF 固定にしてよいか**（＝ Windows で LF のまま開いて問題ないか）:

   - KiCad の S式パーサは**改行を空白（トークン区切り）として扱う**ため、CR の有無で解釈は変わらない。`.kicad_pro` は JSON で、同じく改行は空白。
   - **KiCad 自身が全プラットフォームで LF で書き出す**。つまり LF 固定は KiCad の素の挙動に合わせているだけで、逆に CRLF でチェックアウトすると、Windows の作業者が KiCad で一度保存した瞬間に**全行が LF に書き換わり、ファイル全体が差分になる**（これが避けたかった CRLF ノイズの正体）。
   - したがって「CRLF のつもりで開いたら LF だった」という失敗はそもそも起きない。**懸念があるなら思い込みで CRLF に戻さず、実環境で下記の検証を1回通して確認する**（結果は ADR に残す）:

     ```bash
     # LF 固定のまま KiCad が読める／壊さないことの確認（Windows・Ubuntu 双方で1回ずつ）
     kicad-cli sch erc --exit-code-violations -o outputs/erc.rpt <sch>   # 読めること
     # KiCad GUI で開いて無変更のまま保存 → 差分が出ないこと（出たら改行以外の原因を調べる）
     git diff --stat
     ```

   - 万一 KiCad 以外のツール（社内ツール等）が CRLF を要求する場合も、**リポジトリの正は LF に保ち、そのツールに渡す直前に変換する**。リポジトリ側の改行を変えない。
   - **この検証すら不要にするのが上表の自動チェック**である。仮に LF 固定が効いていない環境があっても、CRLF がインデックスに入った時点で CI が赤くなるため、人間が「どの OS でコミットされたか」を追う必要はない。

2. **`.gitignore`** — KiCad が作業中に生成する一時・バックアップファイルは一切コミットしない（本質的な変更だけを git 管理する）:

   ```gitignore
   # KiCad の自動バックアップ・一時ファイル
   *-backups/
   *.kicad_prl
   *.lck
   ~*.lck
   _autosave-*
   fp-info-cache
   *.bak
   *.bck
   *-bak
   *.kicad_sch-bak
   *.kicad_pcb-bak
   *.tmp
   *.000
   # 生成物（CI が再現生成する）
   outputs/
   # Python
   __pycache__/
   ```

3. **パスは常に相対・大文字小文字も正確に。** 絶対パス（ドライブレター `C:\...` やホームディレクトリ）は OS が変わると解決できない。ライブラリ参照の規則は下記「ライブラリ管理の絶対ルール」。ファイル名の大文字小文字は Ubuntu では区別されるため、参照と実ファイルで正確に一致させる。

### parts.md（部品台帳）のフォーマット

数値・型番の真実の源。**台帳に無い部品・定数を回路図に書かない**（推測禁止。PPTX の「出典の無い数値を書かない」に相当）。

```markdown
| Ref/用途 | MPN | メーカ | パッケージ/フットプリント | データシート | 選定理由 | 状態 |
|---|---|---|---|---|---|---|
| U1 MCU | STM32F103C8T6 | ST | LQFP-48 / Package_QFP:LQFP-48_7x7mm_P0.5mm | <URL> | <理由> | 承認済 / [要確認] |
```

## 環境

- **KiCad のメジャーバージョンをプロジェクトで固定**し、CLAUDE.md「プロジェクト概要」に記録する（S式フォーマットはバージョン間で変わる）。**既定はリリース済みの最新メジャーバージョン（本ガイド執筆時点では 10.x）**とし、より新しいメジャーが出ていればそれを使う。**ただしユーザーが明示的にバージョンを指定した場合はそれに従う。** **エージェントがフォーマットバージョンを上げる保存をしてはならない**（上げる場合はユーザー合意＋ADR）。
- `kicad-cli` のフルパスと Python 実行パスも CLAUDE.md「プロジェクト概要」に記録する（Windows 例: `C:\Program Files\KiCad\10.0\bin\kicad-cli.exe`）。
- Python 依存: `pip install kiutils pytest`（S式操作とテスト用）。

## ライブラリ管理の絶対ルール

1. **グローバルライブラリに依存しない。** 使用するシンボル・フットプリント・3D モデルはプロジェクトローカル（`hardware/<board>/lib/`）にコミットし、`sym-lib-table` / `fp-lib-table` を **`${KIPRJMOD}` からの相対パス**で書く。**絶対パス（ドライブレター・ホームディレクトリ・`KICAD*_3DMODEL_DIR` 等の環境依存変数）は禁止**（Windows / Ubuntu 混在で壊れる）。3D モデルのパスも同様に `${KIPRJMOD}` 相対にする。誰の環境でも・CI でも同一に開けることを保証する。
2. **新規・変更フットプリントは、データシートの推奨ランドパターンとの寸法照合を人間承認ゲートにする。** 照合結果（寸法値の突合表）を PR に添付する。フットプリントの寸法ミスは基板の作り直しに直結する唯一最大のリスク。
3. シンボルのピン番号・ピン名はデータシートと完全一致させる（サブエージェントにデータシートを読ませて突合する）。

## 作成の絶対ルール

1. **`.kicad_sch` / `.kicad_pcb` への書き込みは単一エージェントが直列で行う。** 並列編集は S式破損・UUID 衝突を起こす。サブエージェントに任せてよいのはテキストを返すだけの作業（データシート読解・出図画像のチェック・レビュー）まで。
2. **KiCad GUI が同じファイルを開いている間はスクリプトで書き込まない**（`*.lck` がある場合は停止してユーザーに確認）。
3. **編集のたびに検証を回す**: 保存 → `kicad-cli sch erc`（パース確認を兼ねる）→ 接続テスト。壊れた状態で次の編集に進まない。
4. **parts.md に無い部品・定数を置かない。** 未確定は spec.md に `[要確認]` として残し、承認時に潰す（勝手に埋めない）。
5. 回路図の可読性規約（信号は左→右、電源上・GND 下、ラベル配線優先など）は [workflow_sch.md](kicad/workflow_sch.md) に従う。

## エージェント構成（コンテキスト・計算資源の節約）

| 作業 | 任せ先 | 理由 |
|---|---|---|
| ユーザーとの対話・判断・`.kicad_sch` / `.kicad_pcb` への書き込み | **親**（単一エージェント直列） | 対話と書き込みは分割できない（並列編集は破損する） |
| データシート読解・部品選定調査・ピン割当突合 | **サブエージェント** | PDF はコンテキストが重い。要約（テキスト）だけ親に返す |
| 出図した回路図 PDF / 基板レンダの目視チェック | **サブエージェント** | 画像を親のコンテキストに持ち込まない |
| ERC / DRC / 接続テスト / 出図 / BOM 生成 | **スクリプト** | 決定的な作業はモデルにやらせない（速く・確実・ゼロコンテキスト） |

## 検証ゲート（Definition of Done の読み替え）

PR をレビューに出す前に、以下をすべて満たすこと:

- [ ] **接続テスト全緑**（ネットリスト pytest。テスト緑に相当）
- [ ] **ERC / DRC 警告ゼロ**（抑制する場合は理由を ADR に記録。lint に相当）
- [ ] 回路図 PDF（レイアウト PR なら基板図・3D レンダ）を出図し、目視レビュー済み
- [ ] BOM 全行に MPN・フットプリントが埋まり、`parts.md` と一致（推測部品が無い）
- [ ] [review_checklist.md](kicad/review_checklist.md) の該当セクション全項目クリア
- [ ] `progress.md` 更新済み／spec から逸脱した判断は ADR に記録

**発注（製造データ提出）は PR マージとは別の最終ゲート**とする。review_checklist.md「発注前」セクションを人間と一緒に通してから出す。

## CI

- PR ごとに **ERC + DRC + 接続テスト + 出図** を `kicad/kicad:<version>` Docker イメージ上で自動実行し、出図物（PDF 等）を PR の artifact に添付する（レビュアーが図を見られるようにする）。
- タグ（リリース）で製造データ一式（ガーバー・ドリル・BOM・座標）を生成する。
- 設定手順は [ci_kicad.md](kicad/ci_kicad.md)。

## 修正ループ（レビュー後）

- PR レビュー・ユーザー確認で出た修正は PR コメントとして受け、1件ずつ対応・報告する（`agent_docs/common/pr_review.md` の運用）。
- **ブロック構成・部品選定レベルで違う**（作り直し）と判断された場合は、PR を閉じて**レッド（回路仕様＋接続テスト）に差し戻す**。理由を ADR に記録する。

## 付記: 採らなかった選択肢（必要なら ADR で採用）

- **回路のコード記述（SKiDL / atopile）**: TDD 親和性は最高だが、KiCad 正史ファイルから外れ、人間が GUI でレビューできなくなる。回路図の可読性を捨てられる試作でのみ検討。
- **エージェントによる自動配線**: 対話的・空間的作業のため既定では人間が GUI で行う。freerouting 等を使う場合も DRC＋人間目視を必須とする。
