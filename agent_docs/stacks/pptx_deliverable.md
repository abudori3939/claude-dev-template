# スタックガイド: 文書成果物 / PPTX（資料作成）

成果物が**プログラムではなく PowerPoint 資料（提案書・報告書・納品資料など）**であるプロジェクト用のスタックガイド。
CLAUDE.md の開発フロー（ドキュメント駆動・TDD・ブランチ→PR→レビュー）を、ここで資料作成向けに読み替えて具体化する。

> 付属資料（このガイドとセットで使う）:
> - [`pptx_deliverable/workflow_pptx.md`](pptx_deliverable/workflow_pptx.md) … python-pptx の作業手順とコード雛形（書式を壊さない差し替え方）
> - [`pptx_deliverable/review_checklist.md`](pptx_deliverable/review_checklist.md) … 納品前チェックリスト
> - [`pptx_deliverable/format_rules_template.md`](pptx_deliverable/format_rules_template.md) … 体裁ルール（`agent_docs/project/format_rules.md`）の雛形
> - [`pptx_deliverable/scripts/`](pptx_deliverable/scripts/) … 体裁の実測・テンプレ生成スクリプト

## 開発フローの読み替え（コード ↔ 資料）

CLAUDE.md のフローは変えない。各工程を次のように対応させる。

| コード開発 | 資料作成 | 備考 |
|---|---|---|
| plan.md（どう作るか） | 資料の目的・読み手・利用シーン・ゴールメッセージ・章構成・作業順 | 下記「plan.md に書くこと」 |
| spec.md（何を満たすか） | **骨子（スケルトン）**: A. スライド一覧 ＋ B. スライド詳細 | 2層で育てる原則もそのまま対応（下記） |
| progress.md | 現工程（骨子/初稿/修正/仕上げ）・対象ファイル・合意状態 | 「対象ファイル（最新・唯一の正）」を必ず明記 |
| **レッド**（失敗するテスト） | **骨子（.md）を書き上げ、ユーザーの承認を得る** | この時点で PPTX は作らない。「骨子はあるが満たす資料が無い」＝レッド |
| テスト承認 | 骨子承認（本文文面レベルまで） | 直すならここが最も安い |
| **グリーン**（最小実装） | 骨子どおりに PPTX 初稿を生成 | 骨子からの**転記**が基本。想像で執筆しない |
| **リファクタリング** | 体裁・表記の仕上げ（誤字・表記統一・レイアウト崩れ） | 同じ PR に含める |
| lint / 静的解析 | 検証ゲート（下記）＋ チェックリスト | |
| コードレビュー（PR） | 資料レビュー（PR）: 骨子との一致・体裁・出典を確認 | 修正指示は PR コメントで受け、`agent_docs/common/pr_review.md` の運用に従う |

### 粒度（コードの S/M/L 較正は適用しない）

- **1サイクル（=1 PR）＝資料全体（全スライド）**を既定とする。
- 理由: 資料は**全体の流れ（ストーリー）が品質の本体**であり、章単位の分割レビューでは流れを評価できない。また 1 つの資料は人間が一度にレビューできる情報量に自然に収まるため、コードのような差分制限は不要。
- 例外: 結果集など機械生成の大量ページを含む場合は「説明パートの PR」と「結果集生成の PR」を分けてよい。

### レッドの出力は .md（PPTX ではない）

骨子は Markdown（spec.md）で承認を取る。中間 PPTX を作らないのは、承認の対象を「内容と流れ」に保ち、「見た目」に引っ張られないため。体裁はグリーン以降でテンプレートが保証する。

## リポジトリ構成（このスタックで追加するもの）

このスタックを選択したら、エージェントは最初に以下のディレクトリを作成する（`templates/README.md` の文面は下記「体裁テンプレートの整備」）。

```
├── agent_docs/project/
│   ├── plan.md            ← 資料版として記入（下記）
│   ├── spec.md            ← 骨子（下記フォーマット）
│   ├── progress.md        ← 現工程・対象ファイル・合意状態
│   ├── format_rules.md    ← 体裁ルール（format_rules_template.md から作成）
│   └── data_sources.md    ← 出典台帳（数値・図の元データの所在）
├── templates/
│   ├── README.md          ← 人間向け: 社内フォーマット .pptx の置き場であることを誘導
│   └── フォーマット.pptx     ← コピー元の空テンプレ（直接編集禁止）
├── assets/                ← 図・グラフ画像等の素材
└── outputs/               ← 生成した PPTX の出力先
```

## plan.md に書くこと（資料版）

- **目的**: この資料で誰に何を伝え、何を判断・行動してほしいか
- **読み手**: 役職・専門知識のレベル。社外/社内（社外なら品質基準を明記）
- **利用シーン**: プレゼン/配布/承認、持ち時間・枚数感
- **ゴールメッセージ**: 資料全体の結論を1〜3行で言い切る
- **章構成と作業順**: 章の並びと、機械生成パートの有無
- **粒度**: 既定＝資料全体1PR（例外があればここに明記）

## spec.md（骨子）のフォーマット — 2層で育てる

コードの spec と同じく2層。**Phase 0（骨子の枠組み）で A を、着手時（レッド）に B を書き切る。**

| いつ | 何を書くか | 粒度 |
|---|---|---|
| 計画時 | メタ情報 ＋ **A. スライド一覧**（鳥瞰: タイトル・要点・1行結論・元データ） | 粗い（構成レベル） |
| **レッド（骨子承認前）** | **B. スライド詳細**（実際に載せる箇条書き本文・1行結論・図・出典） | 細かい（本文文面レベル） |

> ⭐ **B. を本文文面まで書き切ってから承認を取るのが肝。** A. の目次レベルで止まると、
> グリーンが想像で本文を執筆することになり、推測混入・手戻りを招く。

```markdown
## メタ情報
- 資料タイトル / 提出先 / 作成日 / 用途・位置づけ
- ゴールメッセージ（全体結論）
- 出典キー: `[1]` <元データ名> / `[2]` ... / `[U]` ユーザ提供の前提

## A. スライド一覧（鳥瞰）
| # | スライドタイトル | 本文の要点 | 1行結論 | 元データ |
|---|---|---|---|---|

## B. スライド詳細（1スライド＝1ブロック）
### Slide N ── <タイトル>
**本文（このまま載せる箇条書き案）**
- <文面> ← [出典キー]
**1行結論**: <このスライドの結論>
**図・素材**: <使う図。新規作図なら明記>
**使う元データ**: [n]
**備考/未確定**: `[要確認]` を明示
```

- 出典の無い数値・固有名詞は**書かない**（推測禁止）。未確定は `[要確認]` として残し、承認時に潰す。
- 結果集など機械生成パートは、1枚ずつ書かず「**機械生成仕様**」（元データ→ページの対応規則・除外・欠落の扱い）を B に書く。

## 体裁テンプレートの整備（最初の1回。コードの環境構築に相当）

1. `templates/` ディレクトリを作成し、**`templates/README.md`** を置いて人間をここに誘導する。文面の例:

   ```markdown
   # templates/ — 体裁テンプレート置き場

   資料の体裁を決めるため、以下のどちらかをこのディレクトリに置いてください。
   - **(A)** 社内標準テンプレートの `.pptx`（あれば）
   - **(B)** 無ければ、体裁の参考にしたい既存資料（提案書・報告書など）の `.pptx` を数点
     → エージェントが共通の体裁（フォント・配色・レイアウト・固有要素）を抽出して
       空のフォーマット（`フォーマット.pptx`）を作ります。

   ここのファイルが直接編集されることはありません（必ず複製して使われます）。
   ```

2. `templates/フォーマット.pptx`（空のコピー元）があるか確認。あれば `scripts/dump_layout.py` で空・一貫を点検して完了。
3. 無ければ**勝手に作らず**、上記 README の (A)/(B) をユーザーに促す:
   - (A) 社内標準テンプレートの .pptx → 中身は除去して空フォーマット化
   - (B) 既存資料数点 → `scripts/analyze_format.py` / `dump_layout.py` で共通体裁を実測し、`scripts/build_format.py` を調整して空フォーマットを生成
4. 確定した体裁（フォント・サイズ階層・配色・固有要素・禁則）を **`agent_docs/project/format_rules.md`** に記録する（[雛形](pptx_deliverable/format_rules_template.md)）。以降の全工程はこれを厳守する。

## 作成の絶対ルール

1. **`templates/フォーマット.pptx` を直接編集しない。** 必ず `outputs/` にコピーして使う。
2. **汎用の pptx 生成ツール／スキルでスライドをゼロから組み立てない。** テンプレ由来の体裁（フォント・配色・固有要素）が失われる。必ず [workflow_pptx.md](pptx_deliverable/workflow_pptx.md) のヘルパーで**既存 run の書式を保ったままテキストを差し替える**。
3. **数値・固有名詞は `data_sources.md` の元データから転記し、推測で書かない。** 骨子の空欄・`[要確認]` を勝手に埋めない（必要ならレッドに差し戻す）。
4. **pptx への書き込みは単一エージェントが直列で行う。** 複数エージェントの並列編集は競合・破損する。サブエージェントに任せてよいのは文面草案・レビューなど**テキストを返すだけの作業**まで。
5. 社外提出物になり得るものとして、誤字脱字・単位・桁・日付・社名表記を必ず検証する。文体は資料内で統一する。

## エージェント構成（コンテキスト・計算資源の節約）

PPTX 作成は、画像の読み込み・大量ページ・全スライドの通し見など**コンテキストを大きく消費する作業**を含む。
親エージェントが高性能・高コストなモデル（例: Opus / Fable）の場合、**すべてを親でやらない**。作業ごとに任せ先を分ける:

| 作業 | 任せ先 | 理由 |
|---|---|---|
| ユーザーとの対話・判断・pptx への書き込み | **親**（単一エージェント直列） | 対話と書き込みは分割できない（並列編集は破損する） |
| 骨子の草案・レビュー、スライド文面の推敲 | **サブエージェント**（軽量モデルで足りるなら Sonnet 等を指定） | テキストを返すだけの作業。並列化・多視点化もしやすい |
| 生成後の画像化した全スライドの目視チェック | **サブエージェント** | 画像は特にコンテキストが重い。親に画像を読み込ませない |
| 大量ページの機械生成・骨子との突合・体裁の実測 | **スクリプト** | 決定的な作業はモデルにやらせない（速く・確実・ゼロコンテキスト） |

- サブエージェントは**要約（テキスト）だけ**を親に返す。画像や全文を親のコンテキストに持ち込まない。
- ユーザーへの質問・pptx の編集はサブエージェントに任せない（サブエージェントは対話できず、並列編集は競合・破損する）。

## 検証ゲート（Definition of Done の読み替え）

PR をレビューに出す前に、以下をすべて満たすこと:

- [ ] **骨子との突合**: spec.md（骨子）のスライド一覧と生成物が過不足なく一致（テスト緑に相当）
- [ ] ファイルが破損なく開ける（python-pptx で再読込 or PowerPoint で開く）
- [ ] 体裁が `format_rules.md` どおり（lint に相当）
- [ ] **画像化して通し見**し、はみ出し・重なり・崩れが無い（目視は必須。別視点のサブエージェントに見せると気づきが増える）
- [ ] [review_checklist.md](pptx_deliverable/review_checklist.md) 全項目クリア
- [ ] `progress.md` 更新済み（対象ファイル名を明記）／骨子から逸脱した判断は ADR に記録

## 修正ループ（レビュー後）

- PR レビュー・ユーザー確認で出た修正は、**PR コメント（または修正指示の一覧表）**として受け、1件ずつ対応・報告する（`agent_docs/common/pr_review.md` の運用）。
- **構成レベルで違う**（作り直し）と判断された場合は、PR を閉じて**レッド（骨子）に差し戻す**。理由を ADR に記録する。

## 実行環境

- **python-pptx** を使う（インストール: `pip install python-pptx`）。
- Windows では `python` 単体がストアシムに当たり失敗することがある。**プロジェクトの CLAUDE.md「プロジェクト概要」に Python 実行パスを記録し、フルパスで呼ぶ。**
- PowerPoint（または LibreOffice）があれば PDF 化→画像化で目視確認に使う。
