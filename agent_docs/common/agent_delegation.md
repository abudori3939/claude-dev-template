# エージェント分業とモデル選択（スタック非依存）

CLAUDE.md「エージェント分業とモデル選択」の詳細版。
**親エージェントが高性能・高コストなモデル（Opus / Fable など）で動いている場合に、何を自分でやり、何を降ろすか**を定める。

## 用語（重要）

このドキュメントで **「コードレビュー」** と書くとき、それは **PR に対する設計レビュー**（CLAUDE.md「ブランチ・PR・レビュー」の工程）だけを指す。
スタックガイドに出てくる「骨子のレビュー」「文面の推敲」「出図画像の目視チェック」などは**この工程ではない**。それらは軽量モデルに降ろしてよい（各スタックガイドの指示に従う）。混同すると「PR レビューを Haiku に降ろす」という真逆の運用になる。

## 原則

> **親は「監督・判断・対話」に専念し、判断の要らない実作業は軽量モデルのサブエージェントかスクリプトに降ろす。**

理由は 2 つ。

1. **コンテキストの節約** … 大量の diff・ログ・生成物の読み込みは親のコンテキストを食い潰す。サブエージェントに読ませ、**要約（テキスト）だけを親に返させる**と親は長く働ける。
2. **計算資源・時間の節約** … 機械的な作業に高コストモデルを使うのは無駄。特に PR レビューは長時間かかる工程なので、周辺作業まで親でやると全体が遅くなる。

## 任せ先の判断表

| 作業 | 任せ先 | 理由 |
|---|---|---|
| ユーザーとの対話・承認取り付け・仕様/設計判断・TDD の方針決定 | **親**（Opus / Fable） | 判断そのもの。サブエージェントは対話できない |
| テストコード・実装本体の記述 | **親**。ただし**plan mode で実装方針が確定し、書く内容が「その方針の書き下し」に過ぎない場合は Sonnet に委譲**し、親が差分を確認する | 設計判断が混ざるので既定は親。委譲したときの親の確認は**受け入れ確認であって PR レビューの代替ではない**（PR レビューは別エージェントで必ず行う） |
| **コードレビュー（PR レビュー）** | **別エージェント。モデルは落とさない（Opus 等）** | レビューは判断そのもの。ここを軽量化すると見落とす。**軽量化の対象外** |
| 骨子・文面の推敲、出図画像の目視チェックなど**スタックガイドが言う「レビュー」** | **Haiku / Sonnet** | PR レビューとは別物（上の「用語」参照）。テキスト・画像を見て所見を返すだけ |
| 大量ファイルの機械的リネーム・定型置換・import 修正・追従修正 | **Haiku** | 判断が要らず、ファイル数だけ多い典型 |
| 差分を読んで **PR 本文（説明・テスト内容・DoD チェック）を書き起こす** | **Haiku / Sonnet** | diff の読み込みがコンテキストを食う。成果物は短いテキスト |
| レビュー指摘のうち、対応方針が確定した機械的な修正の適用 | **Sonnet** | 方針は親が決め、手を動かすのは軽量モデル |
| 長いビルドログ・テスト失敗出力・データシート・仕様 PDF の読解と要約 | **Sonnet / Haiku** | 生データを親のコンテキストに持ち込まない |
| 生成物（画像・PDF・レンダ結果）の目視チェック | **サブエージェント** | 画像は特にコンテキストが重い |
| ビルド / テスト / lint / format / 出力生成 | **スクリプト・コマンドを直接実行** | 決定的な作業はモデルにやらせない（速く・確実・ゼロコンテキスト） |
| `git mv` / `git commit` / `gh pr create` など**単発の決定的コマンド** | **親がそのまま実行** | サブエージェントを起こすほうがオーバーヘッドが大きい |

### よくある取り違え

- **「PR のアップロードは Haiku に任せる」は半分正しく、半分間違い。**
  `gh pr create --title ... --body ...` を撃つこと自体は決定的な 1 コマンドで、コンテキストをほぼ食わない。**そこにサブエージェントを立てるのは純粋なオーバーヘッド**なので親が直接実行してよい。
  軽量モデルに降ろす価値があるのは、その手前の **「差分を読んで PR 本文を書き起こす」** 部分（読み込みが重く、返るものは短いテキスト）。
  → **切り分けの基準は「モデルか否か」ではなく「重い読み込みと判断が要るか否か」。**
- **レビューエージェントを軽量モデルにしてはいけない。** 「レビューは時間がかかるから軽くする」は逆効果で、見落としたバグの手戻りのほうが高くつく。**軽くするのはレビューの前後（PR 作成・指摘の適用・リネーム）であって、レビューそのものではない。**

## 指示の出し方（Claude Code）

- サブエージェントは Agent ツールで起こし、**`model` パラメータでモデルを明示する**（`haiku` / `sonnet` / `opus` / `fable`）。指定しなければ既定のモデルになり、意図した振り分けが効かない。
- **コードレビューエージェントを起動するときも `model` を明示する。** 「既定のサブエージェントモデル」が軽量モデルに設定されている環境では、指定を省くと**黙って軽量モデルでレビューされる**。省略は「落とさない」の保証にならない。
- **`subagent_type: "fork"` は親のモデルを継承し、`model` 指定が無視される。** 軽量化目的では使わない（fork は「親の文脈を丸ごと引き継ぎたい」場合のもの）。
- **サブエージェントには要約（テキスト）だけを返させる。** 画像・全文・生ログを親のコンテキストへ持ち込ませない。
- **ユーザーへの質問はサブエージェントに任せない。** サブエージェントは対話できないため、確認が要る事項は親が聞く。
- **同一ファイルを複数エージェントに同時編集させない**（競合・破損する）。並列化してよいのは「読んで返すだけ」の作業。
- 独立した作業を複数のサブエージェントに任せるときは、**1 回のメッセージでまとめて起こして並列実行**させる。

## やりすぎの禁止

- **降ろす価値があるのは「読む量が多い」か「触るファイルが多い」作業だけ。** 目安として、**親がすでに内容を把握している 1〜2 ファイルの修正**や、**出力が数行のコマンド 1 本**にサブエージェントを立てない（起動・指示・結果受け取りのコストが上回る）。
- サブエージェントの結果を鵜呑みにしない。**受け取った要約の妥当性は親が判断する**（特にレビュー指摘と「テストが通った」という報告）。
