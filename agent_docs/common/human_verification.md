# 人間による確認の手順書（スタック非依存）

システムを組んでの組み合わせテスト（結合テスト）・実機確認・現物照合など、**人間が目で見て判断する工程**を依頼するときの書き方を定める。

> **目的は「目視を省く」ことではなく「目視以外の手間をゼロに近づける」こと。**
> 人間の確認はこのフローで最も遅い工程になりやすい。遅くなる原因の大半は判断そのものではなく、「何を準備すればいいか調べる」「コマンドを組み立てる」「どこを見ればいいか迷う」「失敗したときに原因を探す」といった周辺作業である。エージェントはこの周辺作業を手順書で肩代わりし、**人間は物理操作と判断だけに集中できる状態**を作る。
>
> 人間ゲート・組み合わせテストでの**人間の判断**を、機械判定やサブエージェントの判定に置き換えてスキップしてはならない（人間ゲートの意味がなくなる）。機械にやらせるのは、判断の**前後**（準備・ログ収集・結果の整形）だけ。
> なお、出図画像・スライド画像などをサブエージェントに見せる「目視チェック」（`agent_delegation.md`・各スタックガイド）は**エージェント側の自己点検**であり、この文書の対象外。人間ゲートの代わりにはならない。

## いつ使うか

次のどれかで、人間に操作・確認を依頼するとき**必ず**この形式で手順書を出す。

- 複数モジュール・複数プロセス・実機を組み合わせて動かす**組み合わせテスト（結合テスト）**
- スタック固有の**人間ゲート**（RP2040 / RP2350 の実機ゲート、KiCad のフットプリント現物照合・ガーバー目視など。`agent_docs/stacks/<該当>.md`）
- GUI 操作・センサ観測・音や光など、**エージェントが観測できない結果**の確認

出すタイミングは CLAUDE.md のフローどおり **PR 作成と同時**（レビューと並行して実施してもらう）。結合テストを PR とは別に行う場合も、依頼の時点で同じ形式で出す。

## 手順書の原則

1. **コピペで実行できる完全なコマンドを書く。** 「ビルドしてから起動する」ではなく、実際に打つコマンドを 1 行ずつ書く。`cd` や環境変数の読み込み（`source ...`）も省略しない。
   - プレースホルダは避ける。どうしても環境依存の値（シリアルポート名・IP アドレスなど）が入る場合は、**その値を調べるコマンド**を直前のステップに置き、`<PORT>` のように目立つ形で書いて「ここを置き換える」と明記する。
2. **1 ステップ＝1 操作。** 各ステップに「どの端末／どの機器で」「何をするか」「**期待される出力・見た目**」を書く。複数端末を使う場合は「端末A」「端末B」のように名前を付け、全ステップでその名前を使う。
3. **見るべき場所を指定する。** 長いログのどの行、画面のどの表示、LED のどの色・点滅周期を見ればよいかを具体的に書く（例: 「`ros2 topic hz /scan` の `average rate:` が 9〜11 Hz」「`[sensor] temp=` で始まる行が 1 秒ごとに出る」）。
4. **環境整備を細かく書く。** 初めてその環境を触る人が調べずに済む粒度で書く。特に次を漏らさない。
   - バージョンは固定して書く（「最新」ではなく、このプロジェクトで動作確認したもの）。OS ごとに違う手順は分ける。
   - 再ログイン・再起動・ドライバ再読み込みが必要な操作は明示する（グループ追加後の再ログインなど）。
   - 配線はピン対応表で書き、電源電圧（3.3V / 5V）を必ず書く。
   - IP・ポート番号・ドメイン ID・デバイス名などは、値と**その値を確認するコマンド**をセットで書く。
5. **確認できる前提は、手順の途中で確認させる。** 「インストール済みのはず」で進めず、`--version` やデバイスの列挙など**前提が満たされているかを確かめるコマンドと期待出力**を置く。失敗が手順の後半で発覚すると原因切り分けが重くなる。
6. **エージェントが先に済ませられることは済ませておく。** ビルド・静的チェック・設定ファイル生成・ログ収集スクリプトの用意などは、依頼前にエージェントが実行・確認し、その結果（「全ビルド・単体テストは緑を確認済み」「launch ファイルの構文チェック済み」など）を手順書の冒頭に書く。人間の手順に残すのは**人間にしかできない操作**（書き込み・配線・電源投入・目視・GUI 操作）と、その直前に必要なコマンドだけにする。
7. **物理的な段取り替えが少ない順に並べる。** 配線の付け替え・機器の入れ替えはまとめ、同じ構成で確認できる項目を連続させる。
8. **ログは自動でファイルにも残す。** 観測結果を PR に貼る手間を減らすため、出力を `tee` などで保存するコマンドにしておき、保存先パスを明記する（例: `mkdir -p ~/verify_logs && <コマンド> 2>&1 | tee ~/verify_logs/$(date +%Y%m%d_%H%M%S)_sensor.log`）。

## 手順書のフォーマット

PR 本文またはコメントに、次の見出し構成で書く。項目が該当しない場合は「なし」と書き、見出しは消さない（漏れと「不要」を区別するため）。

> **短縮形**: 確認手順が 1〜2 ステップで、環境整備が不要（前回から変更なし）な小さな確認は、「目的／確認手順（コマンド＋期待出力）／合否基準／結果の報告」の 4 項目だけでよい。**コマンドと期待出力・合否基準は短縮形でも省かない。****修正後の再確認で短縮形を使う場合も、下記「再確認のときも、毎回コマンドを出し直す」の 1〜4（変更点・反映と反映確認・古い成果物の除去・再ビルドから合否確認までの全コマンド）は省かない。**

````markdown
## 人間確認の依頼: <何を確認するか（1行）>

- 目的: <この確認で何を保証するか。spec のどの「完了の目安」に対応するか>
- 所要時間の目安: <例: 初回 30 分（環境整備込み）／2 回目以降 10 分>
- エージェント側で確認済み: <例: native テスト緑、pico / pico2 ビルド緑、launch ファイルの構文チェック済み>

### 0. 必要なもの
- 機材: <型番・個数。例: マイコンボード ×1、USB ケーブル（データ通信対応）×1、センサモジュール ×1、ジャンパ線 ×4>
- PC 環境: <OS・必要なソフトとバージョン>
- 権限・アカウント: <例: シリアルポートへのアクセス権（dialout グループ）>

### 1. 環境整備（初回のみ。済んでいれば 2. へ）
各手順の後に確認コマンドと期待出力を書く。

1. <ソフトのインストール>
   ```bash
   <コマンド>
   ```
   確認: `<確認コマンド>` → `<期待出力>`
2. <権限の設定・再ログインの要否>
3. <配線>（ピン対応を表で書く。可能なら図・写真へのリンク）
   | 機器A のピン | 機器B のピン | 備考 |
   |---|---|---|
4. <ネットワーク・環境変数・設定ファイル>

### 2. 確認手順
1. 【端末A】<操作>
   ```bash
   <コマンド>
   ```
   期待: <出力・見た目。見るべき行・表示を具体的に>
2. 【実機】<物理操作。例: センサの電源を入れる／ロボットを床に置く>
   期待: <例: 端末A のログに `connected` が出る／LED が緑点灯>
3. ...

### 3. 合否基準
- OK: <見れば判断できる形。例: 30 秒間、`temp=` 行が 1 秒ごとに途切れず出て値が 15〜35 の範囲／RViz 上で点群が壁の位置に重なる>
- NG: <典型的な失敗の見え方>

### 4. うまくいかないとき
| 症状 | よくある原因 | 対処（コマンド） |
|---|---|---|

### 5. 後片付け
<プロセスの停止・電源断・配線を戻す、など。なければ「なし」>

### 6. 結果の報告（PR にコメントで貼る）
```text
- [ ] 手順 2-1 〜 2-N を実施した
- 判定: OK / NG
- ログ: <保存したログファイルの中身、または該当部分>
- 気づいた点:
```
````

> 「4. うまくいかないとき」は、そのスタック・その構成で**実際に起きやすい失敗**を書く（USB ケーブルが充電専用、シリアルポートの権限不足、別プロセスがポートを掴んでいる、ROS_DOMAIN_ID の不一致など）。一般論を並べない。

## 再確認のときも、毎回コマンドを出し直す

小さな修正や、目視確認で NG が出た後の修正を経て**再確認を依頼するときも、確認手順のコマンドを毎回すべて出力する**。「前回と同じ手順で確認してください」「手順 2 からやり直してください」で済ませてはならない。

> **なぜ**: 再確認で最も起きやすい失敗は、**修正前の成果物のまま確認してしまう**こと（ブランチを更新していない、再ビルド・再書き込みを忘れた、古いプロセスが残っている、前回のターミナル履歴から古いコマンドを打った）。この場合、確認は「通った」ように見えても修正を何も検証していない。コマンドを出し直すのは、人間が手元の履歴に頼らず、**今回の修正を確実に載せた状態で確認できるようにする**ため。

再確認の依頼には、少なくとも次を含める。

1. **何を変えたか**（1〜3 行）と、それによって**前回と見え方がどう変わるはずか**（今回特に見てほしい箇所）。
2. **修正を手元に反映するコマンド**（例: `git fetch && git switch <ブランチ> && git pull`）と、**反映できたことを確かめるコマンド**（例: `git log -1 --oneline` → `<今回のコミットハッシュ> <件名>` と出ること）。
3. **古い成果物・プロセスを消すコマンド**（必要な場合。クリーンビルド、常駐プロセスの停止、キャッシュ削除など）。
4. **再ビルド・再書き込み・再起動から合否確認までのコマンド全部**（手順書「2. 確認手順」をこの修正版で書き直したもの）。可能なら、**今回の成果物であることを画面上で確かめられる手がかり**（起動ログに出るバージョン・コミットハッシュ・ビルド時刻など）を合否基準の手前に置く。
5. 合否基準と結果報告テンプレ（変わっていなくても再掲する）。

「1. 環境整備」は変更がなければ「前回から変更なし」と書いて省略してよい。**省略してよいのは環境整備だけで、反映〜確認のコマンドは省略しない。**

## 繰り返す結合テストの手順は残す

同じ組み合わせテストを複数回行う場合（機能追加のたびに全体を通すなど）は、手順書を PR に書き捨てず、`agent_docs/project/verification/<確認名>.md` に置いて更新しながら再利用する。PR では差分（今回追加・変更したステップ）と、そのファイルへのリンクを示せばよい。

- 手順の大部分が定型のコマンド列なら、**準備・起動・ログ保存をまとめたスクリプト**（例: `scripts/verify_<確認名>.sh`）を用意してよい。ただしスクリプトがやるのは準備と記録まで。**合否の判断は人間が手順書の合否基準を見て行う。**
- 人間から報告された「つまずいた点」は、次回のために手順書の「4. うまくいかないとき」へ追記する。

## 結果を受け取った後（エージェント）

1. 報告されたログと合否基準を突き合わせ、判定と根拠を PR にコメントする。
2. NG の場合は、原因の仮説と次の手（追加で確認してほしいコマンドを含む）を同じ形式で出す。手順書の不備が原因なら手順書を直す。
3. 実機・結合で見つかった不具合は、**可能な限り自動テストで再現させてから直す**（スタックガイドの方針に従う）。
