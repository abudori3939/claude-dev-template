# PR・レビュー運用（スタック非依存）

ブランチ → PR → レビュー → マージの小さなフローを安定して回すための運用詳細。
CLAUDE.md「ブランチ・PR・レビュー」のゲートを満たしたうえで、PR はここに従って進める。

## 基本フロー

1. 作業ブランチ上で実装する（ブランチの切り方は CLAUDE.md「セッション開始時の判定 / 手順0」）。
2. 実装（グリーン＋リファクタ）が完了したら、実装内容のサマリをユーザーに報告する。**ここで止まらない。**
3. **報告と同時に PR を作成する**（ユーザーの返答を待たない）。
4. **コードレビューエージェント（実装者とは別エージェント）**を起動してレビューを開始し、**GitHub の PR 上にコメント**を返させる（レビューを GitHub 上で管理する）。
5. **レビュアー（レビューエージェント）とレビュイー（実装エージェント）が PR 上で会話形式で往復し、収束させる**（下記「レビュー往復ループ」）。
6. **収束したら、マージ前の締めとして `progress.md` を「この PR の作業が完了した状態」に更新し、同じ PR にコミット・push する**（下記「マージ前の締め（progress.md）」）。
7. 締めコミットを push してからユーザーに通知する。ユーザーもレビューに参加し、疑問が解消されるまで PR 上でやり取りを続ける。
8. CI が緑で、`progress.md` が締められていることを確認し、ユーザーが問題ないと確認したらマージする。

> **なぜ止まらないか**: コードレビューは 1 サイクルで最も時間がかかる工程。ユーザーの承認待ちで直列に積むと、待ち時間とレビュー時間が足し算になる。先にレビューを走らせ、**ユーザーの確認とレビューを並行させる**。
>
> **減らすのは「グリーン後・PR 作成前」の停止だけ。** 着手ゲート・レッド確認・テスト承認、およびスタック固有の人間ゲート（KiCad のフットプリント照合、RP2040/RP2350 の実機ゲート等）は残る。**実装完了以降**の承認ゲートが「マージ前」1 か所になる、という意味。
>
> **人間ゲートが必要なスタックでは、PR 作成と同時に手順と合否基準を提示する**（`agent_docs/stacks/<該当>.md`）。レビューと並行して人間に実施してもらい、**結果が PR に記録されるまでマージしない**。

**PR を作る前に一度ユーザーに確認する条件**（これ以外では止まらない）:

- ADR に記録すべき設計判断をした（計画ドキュメントからの逸脱）
- `spec.md` の**層1**（システム全体 I/O・モジュール間インターフェース）を変更した
- **テスト承認時にユーザーへ説明した前提**（ピン割当・プロトコル・データ形式・閾値など）を変えた
- 差分が `plan.md`「フェーズ粒度の方針」の較正レベルを明らかに超えた

## PR 作成・レビューの分業（モデル選択）

規約は `agent_docs/common/agent_delegation.md`。この工程での要点だけ:

- **PR 本文の起草は軽量モデル（Haiku / Sonnet）に降ろしてよい。** 差分を読むのはコンテキストが重く、返るのは短いテキスト。「対応する計画フェーズ／機能」「テスト内容」「DoD チェック結果」を書かせる（`coding_standards.md`「コミット・PR」）。
- **`gh pr create` と、レビュイーとしての `gh pr comment` は親が直接撃つ。** 単発の決定的コマンドにサブエージェントを立てるのはオーバーヘッドのほうが大きい。**レビュアーの指摘コメントはレビュアー本人が投稿する**（親は中継も編集もしない。下記「レビュー往復ループ」）。
- **レビューエージェントのモデルは落とさない**（実装者と別エージェント、かつ同等以上のモデル）。レビューは判断そのもので、見落としの手戻りが最も高くつく。
- **指摘の適用は分ける**: 「どう直すか」は親が決め、**確定した機械的な修正の適用は Sonnet に降ろす**。

## 役割分担

- 実装エージェントとコードレビューエージェントは**必ず別**にする（自分の実装を自分でレビューしない）。
- 機械的な指摘（format / lint / 静的解析）は自動ゲートに任せ、レビューは**設計判断**に集中する。

## レビュー往復ループ（レビュアー ⇄ レビュイー）

PR のレビューは、**レビュアーとレビュイーの会話として GitHub の PR 上に残す**。人間が後から PR を開けば、何を指摘され・どう判断し・どう収束したかを会話として追えるようにするのが目的。

### 登場人物
- **レビュアー** … 実装者とは**別に起動した**レビューエージェント（モデルは落とさない。`agent_delegation.md`）。**指摘コメントはレビュアー本人が PR に投稿する**（親は中継も編集もしない）。
- **レビュイー** … 実装エージェント（通常は親）。指摘ごとに対応する／しないを判断し、PR に返答する。

> 同じ GitHub アカウントから投稿されるため、**コメント冒頭に必ず話者ラベルを付ける**: `**[Reviewer] Round N**` / `**[Reviewee] Round N**` / `**[User]**`（ユーザーの判断をエージェントが代筆して残す場合）。**インラインコメント・スレッド返信にも同じラベルを付ける**。ラベルの無いコメントは会話として追えない。

### 往復（Round）の数え方
**Round N ＝ `[Reviewer] Round N` のコメント ＋ それに対する `[Reviewee] Round N` の返答**。往復数はこの N で数える。

1. **レビュアー（Round N）**: PR にレビューコメントを投稿する。指摘には番号と重要度（**Blocking / Non-blocking**）を付ける。行に紐づく指摘はインラインコメント（スレッド）にしてよい。Round 2 以降は、前 Round の返答と新しい差分を確認し、対応の妥当性・反論への応答・新たな問題を書く。
2. **レビュイー**: 各指摘について **対応する／しない** を判断する。
   - **対応する** → 修正を実装してコミット・push する（テスト・lint を通してから）。
   - **対応しない** → 理由を書く（仕様外・計画どおり・別 PR で扱う、など）。言いなりにならず、技術的に妥当でない指摘には根拠を示して反論してよい。
   - 判断の結果が「PR を作る前に一度ユーザーに確認する条件」（層1変更・ADR 相当の設計判断・テスト承認時の前提変更・粒度超過）に当たる場合は、**実装する前にユーザーに確認する**。
3. **レビュイー（Round N）**: 指摘ごとの「対応した（どう直したか・コミット）／対応しない（理由）」を**追加コメント**で返答し、レビュアーに Round N+1 を依頼する（下記「指摘への対応」の作法に従う）。

レビュアーは**前 Round からの文脈を保ったまま**続ける（同じレビューエージェントに `SendMessage` で続きを依頼する。続けられない場合は新しいレビューエージェントに PR の会話全体を読ませてから再開する）。

### 終了条件
判定するのは**レビュイー（親）**。各 Round のレビュアーコメントを受け取った時点で判定する。

| 状態 | 判定 | エージェントの行動 |
|---|---|---|
| **収束** | レビュアーが「Blocking なし・残る Non-blocking はすべて対応済みか、対応しない理由に合意」と明言した | ループを終え、**先に `progress.md` を締めて push し**（下記「マージ前の締め」）、それから**ユーザーに通知する**（往復数・対応した／しなかった指摘の要約・締めコミット・PR の URL）。マージはユーザーの確認後 |
| **発散** | 次のいずれか: ①同じ指摘で対応する／しないの主張が **2 Round 続けて平行線** ②Blocking の件数が **3 Round 連続で減らない** | ループを止め、**論点を整理してユーザーに判断を仰ぐ**（双方の主張と選択肢を短く示す）。ユーザーの判断を `**[User]**` ラベルで PR に残してから再開する |
| **上限** | **Round 10** に達した | 収束していなければ**必ずユーザーに現状を報告する**（未解決の指摘・止まっている理由・収束の見込み）。**見込みが見えないなら停止**し、ユーザーの指示があるまで再開しない |

> 発散の判定は Round 10 を待たない。平行線が見えた時点で早めにユーザーへ上げるほうが、レビュアーとレビュイーの時間を無駄にしない。

### 収束通知後のユーザー指摘
収束を通知したあとにユーザーが指摘した場合は、レビュイーが `**[Reviewee]**` ラベル（Round 番号なし）で同じ作法により対応・返答する。これは往復数に数えない。修正が大きい（Blocking 相当の変更が入った）場合は、レビュアーに次の Round を依頼して再確認させる。

## マージ前の締め（progress.md）

**収束〜マージの間に、必ず `progress.md` を「この PR がマージされた後の状態」に書き換えるフェーズを挟む。** これを飛ばすと、マージのたびに `main` の `progress.md` が 1 つ前の状態に取り残され、次のセッションのエージェントが終わった作業を「次のタスク」と誤認する。

- **タイミング**: 収束を判定した直後、**ユーザーに収束を通知する前**に行う。PR 作成時点の `progress.md` は「実装済み・レビュー中」の状態でよいが、そのままマージしてはならない。
- **書く内容**（マージ後に `main` で読まれる前提で書く。「レビュー中」「マージ待ち」のような一時状態を残さない）:
  - **完了項目**: この PR で終えた機能・タスクにチェックを付け、PR 番号を添える（例: `- [x] 機能1: 〇〇（PR #14）`）。
  - **現在地**: 次に着手するフェーズ／機能に進める。
  - **次のタスク**: 終えたものを消し、次に着手するものを先頭に置く。
  - **未解決事項**: レビューで「別 PR で扱う」とした指摘や、新たに判明した課題を追記する。解消したものは消す。
- **反映**: 締めの変更は**同じ PR の作業ブランチにコミット・push する**（コミットメッセージ例: `progress.md を締める（PR #14 完了）`）。マージ後に `main` で直すのは手順0違反になるので、必ずマージ前に行う。
- **収束通知後に修正が入った場合**: 締めた内容とずれる変更（対応範囲の追加・先送りの発生など）が入ったら、マージ前に `progress.md` を再度合わせる。
- **ドキュメントだけの PR・テンプレート自身の PR でも省略しない。** `progress.md` に影響しない PR なら、その旨（「progress.md 変更不要」）を収束通知に一言書く。

## 指摘への対応（重要）

PR でレビュー指摘を受けて修正したあとは、**対応状況を必ず「追加コメント」で報告する。**

- **最初の（説明）コメントを編集で上書きして最新化してはならない。** 上書きすると、どの指摘にどう対応したか／対応しなかったかの履歴が消え、人間が追跡できなくなる。
- 修正後は**新しいコメントを追加**して報告する。指摘ごとに「**対応した**（どう直したか）／**対応しない**（その理由）」が分かるように書く。
- 指摘がレビューコメントのスレッドに紐づく場合は、**そのスレッドに返信する形**で対応を書くと、指摘と対応の対応関係が明確になる。

## マージ条件

- CI（build + test + lint）が緑。
- レビュー指摘が解消され、ユーザーが承認した。
- **`progress.md` が締められている**（この PR の作業が完了項目に入り、現在地・次のタスクが次の作業を指している。上記「マージ前の締め」）。締めコミットが無い PR はマージしない。
- 「PR で合格したコードのみマージ」は判断基準を**緑チェック**に置く（CI が緑でない PR はマージしない）。
  - ただし**ブランチ保護は前提としないため、必須チェックとしての強制はかからない**（`agent_docs/common/remote_setup.md`）。マージ前に PR の CI が緑であることを目視で確認する。
