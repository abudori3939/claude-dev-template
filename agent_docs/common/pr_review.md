# PR・レビュー運用（スタック非依存）

ブランチ → PR → レビュー → マージの小さなフローを安定して回すための運用詳細。
CLAUDE.md「ブランチ・PR・レビュー」のゲートを満たしたうえで、PR はここに従って進める。

## 基本フロー

1. 作業ブランチ上で実装する（ブランチの切り方は CLAUDE.md「セッション開始時の判定 / 手順0」）。
2. 実装（グリーン＋リファクタ）が完了したら、実装内容のサマリをユーザーに報告する。**ここで止まらない。**
3. **報告と同時に PR を作成する**（ユーザーの返答を待たない）。
4. **コードレビューエージェント（実装者とは別エージェント）**を起動してレビューを開始し、**GitHub の PR 上にコメント**を返させる（レビューを GitHub 上で管理する）。
5. ユーザーもレビューに参加し、疑問が解消されるまで PR 上でやり取りを続ける。
6. CI が緑で、ユーザーが問題ないと確認したらマージする。

> **なぜ止まらないか**: コードレビューは 1 サイクルで最も時間がかかる工程。ユーザーの承認待ちで直列に積むと、待ち時間とレビュー時間が足し算になる。先にレビューを走らせ、**ユーザーの確認とレビューを並行させる**。
>
> **減らすのは「グリーン後・PR 作成前」の停止だけ。** 着手ゲート・レッド確認・テスト承認、およびスタック固有の人間ゲート（KiCad のフットプリント照合、RP2040/RP2350 の実機ゲート等）は残る。**実装完了以降**の承認ゲートが「マージ前」1 か所になる、という意味。
>
> **人間ゲートが必要なスタックでは、PR 作成と同時に手順と合否基準を提示する**（`agent_docs/stacks/<該当>.md`）。レビューと並行して人間に実施してもらい、**結果が PR に記録されるまでマージしない**。

**PR を作る前に一度ユーザーに確認する条件**（これ以外では止まらない）:

- ADR に記録すべき設計判断をした（計画ドキュメントからの逸脱）
- `spec.md` の**層1**（システム全体 I/O・モジュール間インターフェース）を変更した
- **テスト承認時にユーザーへ説明した前提**（ピン割当・プロトコル・データ形式・閾値など）を変えた
- 差分が `plan.md`「フェーズ粒度の方針」の較正レベルを明らかに超えた

## PR 作成・レビューの分業（モデル選択）

規約は `agent_docs/common/agent_delegation.md`。この工程での要点だけ:

- **PR 本文の起草は軽量モデル（Haiku / Sonnet）に降ろしてよい。** 差分を読むのはコンテキストが重く、返るのは短いテキスト。「対応する計画フェーズ／機能」「テスト内容」「DoD チェック結果」を書かせる（`coding_standards.md`「コミット・PR」）。
- **`gh pr create` / `gh pr comment` の実行自体は親が直接撃つ。** 単発の決定的コマンドにサブエージェントを立てるのはオーバーヘッドのほうが大きい。
- **レビューエージェントのモデルは落とさない**（実装者と別エージェント、かつ同等以上のモデル）。レビューは判断そのもので、見落としの手戻りが最も高くつく。
- **指摘の適用は分ける**: 「どう直すか」は親が決め、**確定した機械的な修正の適用は Sonnet に降ろす**。

## 役割分担

- 実装エージェントとコードレビューエージェントは**必ず別**にする（自分の実装を自分でレビューしない）。
- 機械的な指摘（format / lint / 静的解析）は自動ゲートに任せ、レビューは**設計判断**に集中する。

## 指摘への対応（重要）

PR でレビュー指摘を受けて修正したあとは、**対応状況を必ず「追加コメント」で報告する。**

- **最初の（説明）コメントを編集で上書きして最新化してはならない。** 上書きすると、どの指摘にどう対応したか／対応しなかったかの履歴が消え、人間が追跡できなくなる。
- 修正後は**新しいコメントを追加**して報告する。指摘ごとに「**対応した**（どう直したか）／**対応しない**（その理由）」が分かるように書く。
- 指摘がレビューコメントのスレッドに紐づく場合は、**そのスレッドに返信する形**で対応を書くと、指摘と対応の対応関係が明確になる。

## マージ条件

- CI（build + test + lint）が緑。
- レビュー指摘が解消され、ユーザーが承認した。
- 「PR で合格したコードのみマージ」は判断基準を**緑チェック**に置く（CI が緑でない PR はマージしない）。
  - ただし**ブランチ保護は前提としないため、必須チェックとしての強制はかからない**（`agent_docs/common/remote_setup.md`）。マージ前に PR の CI が緑であることを目視で確認する。
